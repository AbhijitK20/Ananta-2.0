# FEATURES — Ananta

> Every feature below states its purpose, the user story it serves, what goes in,
> what comes out, how you know it works, and what it does when reality breaks.
>
> Types referenced here are the frozen contract in [`src/contracts/index.ts`](../src/contracts/index.ts).
> Nothing in this document is a measurement. Measured numbers live in
> `docs/EVAL_RESULTS.md`, which is generated by `npm run eval`; until that file
> exists, no number in this repo is a result.

## The problem

A traveller in Mumbai has three hours, ₹1,500, four people including a toddler,
an older relative who cannot manage stairs, and a monsoon sky. Every discovery
tool answers a different question: *"what is good near here."* Nobody answers
*"what actually fits."*

The same failure runs the other way. The potter, the Koli fishing community, the
Textile Museum guide — none of them can reach the traveller standing two
kilometres away who would love what they do.

Both are one problem: there is no shared, structured, timely representation of
**what fits whom, where, and when**.

Ananta's whole design follows from one rule:

> **A recommendation must fit, or it is not shown. And when it is not shown, we
> say which constraint killed it, by how much.**

Everything below is either that rule or a consequence of it.

### What is real and what is seeded

Stated here because it belongs in the spec, not in a footnote.

| Real | Seeded |
|---|---|
| The feasibility gate, scoring, packing, validation and replanning | The catalogue. Every record in `content/**` carries `synthetic: true` and a `__meta.estimateBasis` |
| The 20 isochrone polygons and travel-time matrices in `data/reference/isochrones/` | The review set — useful because it is structured and open-vocabulary, not because anyone wrote it after visiting |
| The 1,739-preset coverage measurement, re-derivable from the committed JSON | The Unmet Demand log. There are no users, so it is seeded |
| Every claim about what OSM does and does not carry | The slot availability and booking history |

There are no users, so every count in a Provider Opportunity is currently a seeded
count. The mechanism that produces a count is real; the count is not. In a
presentation that distinction gets volunteered, not discovered.

## 1. The two users

| | Traveller | Provider |
|---|---|---|
| **Who** | On the ground, between commitments, with a hard stop time. Not planning a two-week trip. | A potter, guide, musician, food-stall owner, festival organiser. No marketing budget, no time for a marketplace. |
| **Question** | "What can I actually do right now?" | "Who nearby wanted what I do, and why did they not get it?" |
| **Surface** | Responsive web app, phone-first, one-handed | Provider console, desktop-first |
| **Success** | A plan they complete that they say fits | A booking request, or a listing gap worth filling |
| **Explicitly not** | The itinerary optimiser planning a whole trip in advance | — |

The provider is not a storefront bolted on. Every `Rejection` the traveller is
shown is the same record that becomes the provider's demand signal. One log, two
products.

## 2. Feature: context-aware discovery

**Purpose.** Replace a search box with a description of the traveller's actual
situation, so the engine can reason about fit instead of relevance.

**User story.** *As a traveller standing on a street, I want to say what my
constraints are and get an answer in under 30 seconds, without filling in a
20-minute form.*

**Input.** A `DiscoveryContext`:

| Field | Meaning |
|---|---|
| `origin` | free-text label + resolved `GeoPoint` |
| `availableMin` | minutes from now until they must leave. **The primary constraint.** |
| `nowMin` | wall clock, minutes from local midnight IST |
| `budget` / `budgetPerPerson` | integer paise, never floats |
| `partySize` / `partyType` / `childAges` | drives group fit |
| `accessNeeds` | `wheelchair` · `stroller` · `lowStairs` · `hearingLoop` · `restroom` |
| `diets` | open vocabulary: `vegetarian`, `jain`, `halal` |
| `interests` / `avoid` | the positive and the negative channel |
| `weather` | condition + `source: live \| simulated \| unknown` |
| `travelMode` | preference; we surface a faster alternative anyway |
| `requests` | `DecomposedRequest[]` from natural language |
| `excludedIds` / `pinnedIds` | prior rejections, and what they insist on |
| `original` | **never mutated.** The replan diffs against this. |

**Output.** A `Plan` — a chained, time-boxed itinerary, not a ranked list. Each
`PlanStop` carries a `Fit` and a `ScoreBreakdown`.

**Acceptance criteria.**

- The plan is a chain: every consecutive pair has a `TravelLeg` with mode, minutes
  and metres, and the legs sum to the reported `totalMetres`.
- `totalMin ≤ availableMin`. A plan that overruns the window fails validation.
- `utilisation = plannedMin / availableMin` is reported on every `Plan`, so
  "respects your window" is a number, not a claim.
- Budget is enforced as `pricePerPerson × partySize ≤ budget`, with an optional
  stricter per-person ceiling applied on top.
- Every control writes straight into the `DiscoveryContext`. No shadow state, no
  apply button.
- The context is deep-linkable: the same context reproduces the same `Plan`.
- The context is completable in under 30 seconds on a phone.

**Failure behaviour.**

- **Origin does not resolve** → fall back to the city centroid from
  `CityManifest`, label the position as approximate, and say so.
- **Zero results** → cause-branch, not an empty list. Name the cheapest
  constraint to relax and offer it as a one-tap action.
- **One result and it is tight** → offer the specific number of minutes that
  would fit a second option.
- **Only one category survived** → say so explicitly, and offer the nearest
  alternative category.
- **Weather source unavailable** → `source: 'simulated'`, visibly labelled. Never
  silently presented as a live forecast.
- **Everything nearby is closed** → report the next opening time from
  `OpeningHours`, do not show closed places as available.

## 3. Feature: the feasibility gate

**Purpose.** Make fit a gate rather than a weight. A hard-constraint failure is
deletable; a preference is rankable. Mixing the two is how recommenders show you
places that cannot work.

**User story.** *As a traveller, I want anything that cannot work to be removed
before I see it, so my time is not spent on a closed museum.*

**Input.** `RetrieveInput` — a `DiscoveryContext` plus candidate `Experience`
rows.

**Output.** `FeasibleResult` = `{ passed: string[], rejected: Rejection[] }`.
**Every** dropped candidate emits a `Rejection`. There is no silent drop.

**The twelve checks**, cheapest first, with the `RejectionCode` each one emits:

| # | Check | Codes |
|---|---|---|
| 1 | isochrone contains the origin | `too_far` |
| 2 | travel + duration + buffer ≤ window | `travel_time_exceeds_budget`, `duration_exceeds_budget` |
| 3 | open for the whole visit window | `closed_now`, `closed_during_window`, `hours_unverified` |
| 4 | price × party ≤ budget | `over_budget`, `over_budget_per_person` |
| 5 | capacity ≥ party size | `capacity_exceeded` |
| 6 | every `AccessNeed` satisfied | `not_step_free`, `not_stroller_ok`, `no_low_stairs`, `no_hearing_loop`, `no_restroom`, `inaccessible` |
| 7 | diets satisfiable | `diet_mismatch` |
| 8 | slot not sold out | `sold_out` |
| 9 | bookable with enough notice | `requires_booking_not_available`, `lead_time_too_short` |
| 10 | safe in this weather | `weather_unsafe` |
| 11 | not already planned or excluded | `duplicate`, `already_planned`, `excluded_by_traveller` |
| 12 | in season | `seasonal_mismatch` |

**Acceptance criteria.**

- A `Rejection.message` is a **finished sentence with the real number in it**:
  *"Needs 40 min more than you have left."* Never *"constraint violated."*
- `Rejection.shortfall` and `unit` are populated whenever a number explains the
  failure, so the UI can say "short by 40 min" or "over by ₹300".
- `relaxable` is true when relaxing that one constraint would fix it. This drives
  the Replan ladder.
- **Absent is `unknown`, never `fail`.** `Accessibility` fields are tri-state
  booleans for exactly this reason: OpenStreetMap's `wheelchair` field is
  three-state, so `null` is a real state and must not collapse to `false`. A gate
  that vetoes on missing data deletes most of the catalogue before ranking starts.
- Constraint satisfaction is a pass/fail metric with no averaging. Target 100% by
  construction; measured by `npm run eval`.

**Failure behaviour.**

- `OpeningHours.status === 'unparsable'` → emit `hours_unverified` with
  `relaxable: true`. The gate degrades to soft; it does not throw and it does not
  silently pass.
- The npm `opening_hours` port does not support `PH off` or inline comments. That
  is a parse failure, handled, not a crash.
- An unknown `AccessNeed` value cannot reach this stage: `AccessNeed` is a Zod
  enum, so the input fails validation at the boundary.

## 4. Feature: explainability

**Purpose.** Make the engine's reasoning inspectable. A recommendation you
cannot interrogate is a vibe.

**User story.** *As a traveller, I want to know why each place was chosen and why
the place I asked for is missing, in plain sentences with numbers.*

**Input.** `Fit`, `ScoreBreakdown`, `Rejection[]`, `Experience.provenance`.

**Output.** Three surfaces:

| Surface | Backs | Content |
|---|---|---|
| **Why this** | `ScoreBreakdown.components` | contributions in descending order of impact, each a finished sentence |
| **Why not that** | `Rejection` | one specific reason, the shortfall, and up to three actions |
| **Feasibility meter** | `Fit` | `activity ▸ travel ▸ buffer` against the remaining window, overflow in the alarm colour, plus per-constraint pass/fail |
| **Provenance badge** | `Provenance` | `curated` · `provider` · `osm` · `inferred` · `derived` on every field that is not `curated` |

**Acceptance criteria.**

- Every `PlanStop` has a non-empty `why[]`.
- Every `Experience` field that is not `curated` has a `provenance` entry, and
  anything `inferred` shows a visible badge plus its confidence.
- `ScoreBreakdown.profileVersion` is present, so a score stays auditable after the
  weights change.
- Tapping anything that did not appear returns a **specific** answer, not an empty
  list — the gate keeps `Rejection` rows for candidates the traveller asked about,
  not only for ones they saw.
- The "why not that" answer offers three actions, each a real mutation of the
  `DiscoveryContext`: add the missing time, show what fits the smaller window, or
  pin one stop and re-pack around it.

**Failure behaviour.**

- A `Rejection` with no explainable number shows the code's sentence with no
  figure rather than inventing one.
- If `provenance` is missing for a field, the badge renders as unknown. We do not
  default to `curated`, because that would launder a guess as a fact.

## 5. Feature: routing

**Purpose.** Make "two hours" mean two hours. A list of places with no travel time
between them is not an itinerary.

**User story.** *As a traveller, I want to know the walk between two stops and
whether the chain actually fits my window.*

**Input.** Origin and destination `GeoPoint`s, `TravelLegMode`,
`DiscoveryContext.nowMin` (for the time band), `CityManifest`.

**Output.** `TravelLeg { fromId, toId, mode, minutes, metres, detail, estimated }`.

**Acceptance criteria.**

- Cluster-then-route, not TSP on the raw shortlist. Maximum-clique peeling
  (Bron–Kerbosch) on a radius graph gives diameter-bounded clusters with no `k` to
  tune and no empty-cluster problem. Then cheapest-insertion → 2-opt → Or-opt
  within each cluster, and clusters stitched at their closest pair.
- Every `TravelLeg` sets `estimated`. Modelled estimates are never presented as
  live routing results.
- Travel time comes from a routing facade with a committed fallback chain, and a
  congestion multiplier selected by IST clock, because free-flow times understate
  peak Mumbai.
- Committed isochrone polygons (Bandra West, pedestrian and auto, 5/10/15/20/30
  minutes, from `valhalla1.openstreetmap.de`) are used in preference to a radius.
  A 3 km crow-flies disc is wrong in both directions at once: it is 3.2× the true
  30-minute walking area, and it excludes 73% of the true 30-minute driving area.
- Median travel per stop stays under 1.8 km. A plan that crosses the city twice is
  wrong for this product.

**Failure behaviour.**

| Dependency | Fallback |
|---|---|
| Routing API down | haversine × mode speed factor, `estimated: true` |
| Isochrone unavailable | radius prefilter, flagged as approximate |
| Transit corridor not seeded | haversine estimate; `detail` says the mode is a guess |
| No network at all | committed snapshot; the demo path does not touch the network |

## 6. Feature: scoring and personalisation

**Purpose.** Rank what survived the gate, and let the traveller see and edit what
the system learned about them.

**User story.** *As a returning traveller, I want Ananta to weight my preferences
the way I do — and to show me the weights, so I can correct them.*

**Input.** Surviving `Experience` rows, the traveller's `WeightProfile`, and the
`Interaction` stream (`impression`, `click`, `save`, `book_requested`, `dismiss`,
`not_interested`, `reported_inaccurate`, `opened_directions`, `shared`).

**Output.** `ScoreBreakdown { total, components[], profileVersion,
learnedComponents[] }`.

**Components:** interest match, Bayesian-smoothed rating, value for money, local
authenticity, weather fit, peak-hour crowd penalty, novelty against what is
already planned, group fit, superlinear travel-friction penalty, provider
reliability.

**Acceptance criteria.**

- **One scalar, split into named components.** Never mix `minimize` and
  `maximize` on a shared objective — that lexicographic ordering is exactly what
  silently defeats a relaxation.
- Ratings are Bayesian-smoothed toward the regional prior, and `Rating` carries
  `value`, `count` and `rawMean` so the shrinkage is visible.
- Learned weights come from a Thompson-sampling bandit over the interaction
  stream, are labelled `source: 'learned'`, and are shown to the traveller with
  an `observations` count.
- `source` is `prior` · `learned` · `user_edited` and is **never** mixed
  silently. A stated preference and an inferred one are different things.
- Weights are editable and deletable. Nothing is learned about a traveller
  without being shown to them.

**Failure behaviour.**

- A new traveller has `source: 'prior'` and `observations: 0`. Cold start is the
  prior profile, and the UI says so rather than implying it has learned something.
- A component with too few observations falls back to the prior weight for that
  component, and `observations` is shown next to it.
- `reported_inaccurate` is a first-class interaction type: a traveller can tell us
  a fact is wrong, which is a data-quality signal, not a complaint.

## 7. Feature: chat

**Purpose.** Let a traveller change their situation in words, without learning
the schema.

**User story.** *As a traveller, I want to say "my aunt can't do stairs" and have
that become a hard constraint, rather than a search term.*

**Input.** Free text plus the current `DiscoveryContext`.

**Output.** A `DialogueDecision` — and it is the **only** model output in the
product that is allowed to affect anything:

```ts
{ contextPatch: {...}, reply: string, confidence: number, suggestions: string[] }
```

`contextPatch` may set `availableMin`, `budgetMinor`, `partySize`, `accessNeeds`,
`interests`, `avoid`, `indoorOnly`, `mood`. That is the whole surface.

**Acceptance criteria.**

- The model **cannot** name a recommendation, reorder a plan, or edit a
  feasibility result. Enforced by a test that fails the build if `DialogueDecision`
  widens.
- `confidence >= 0.5` to act. Below it, ask a clarifying question instead of
  guessing. The threshold is borrowed from Plan-It, which gates the same way.
- A question is not a mutation. "Is it far?" must be answerable from the `Plan`
  with an empty `contextPatch`.
- Model output is parsed with a real schema parser, never `JSON.parse` on a string
  we then trust.
- The reply states what changed: *"Cut two stops, kept step-free. Here's why."*
- Tapping a suggestion chip is a first-class path, not a fallback. People should
  not have to type to use the demo.
- The eval suite passes with `LLM=off`.

**Failure behaviour.**

| Failure | Behaviour |
|---|---|
| Model times out or rate-limits | Deterministic regex/keyword parser produces the same `DiscoveryContext` |
| Model returns malformed output | Schema parse fails, `degraded: true`, deterministic parser takes over |
| `confidence < 0.5` | Clarifying question rendered as a chip, not a paragraph |
| No model configured at all | The chat still works; it is a keyword parser with a UI |

## 8. Feature: replanning

**Purpose.** Handle the moment reality diverges from the plan, without discarding
what the traveller originally wanted.

**User story.** *As a traveller, I want to say "it started raining" or "we lost 90
minutes" and get a plan that still matches my goal, with a minimal diff.*

**Input.** The current `Plan` + a `ContextChange` (from a button, a slider, or
`DialogueDecision.contextPatch`).

**Output.** A `ReplanResult { plan, change, swaps[], preservedIntent, summary }`.

**Acceptance criteria.**

- **`DiscoveryContext.original` is kept forever and the replan diffs against it**,
  never against the last mutation. This is the difference between adapting a plan
  and quietly replacing someone's goal.
- `Swap { removedId, addedId, reason, scoreDelta }` — every swap carries a written
  reason and what it cost in score.
- `preservedIntent: true` is asserted on the result and shown in the UI, alongside
  the original interests.
- Target: **≤ 2 swaps per context change.** If a replan returns five, the engine
  is wrong, and that is a finding rather than a state to ship.
- When nothing can be made to fit, the engine walks a **named** ladder and says
  which rung it used and what it gave up:

| Rung | What it gives up |
|---|---|
| `strict` | nothing |
| `dropped_minimum` | minimum two stops → one |
| `greedy_fill` | ordering optimality; just fill the window |
| `single_best` | the whole plan is one option |

- If the first stop sells out, the rest are pinned and only the minimum
  replacement is solved for, so nothing else moves and nothing duplicates.

**Failure behaviour.**

- A context change that invalidates every stop → `single_best`, with a summary
  that says the window is now too short for a chain.
- A weather change with no indoor alternative → the plan shrinks and says why,
  rather than showing rain-soaked outdoor stops.
- A budget cut below the cheapest remaining option → unmet demand is logged
  (§10) and the traveller is told what price would have worked.

## 9. Feature: provider listings and availability

**Purpose.** Let a local provider describe what they offer, accurately enough for
the gate to rely on it.

**User story.** *As a provider, I want to set my duration, price, capacity and
accessibility once, and have them respected by every plan I appear in.*

**Input.** A `Provider` record plus provider-owned fields on `Experience`:
duration, price per person, capacity, the six accessibility booleans, kid-friendly
and minimum age, indoor/outdoor/covered, diets, cuisines, best time of day,
booking requirements.

**Output.** An `Experience` row with `providerId` set and `provenance` on every
provider-submitted field.

**Availability.** `Slot` holds `capacity` and a `held` breakdown. There is
deliberately **no `remaining` field**: availability is *derived* by subtracting
committed counts in priority order — confirmed orders, then pending, then carts.
That makes overselling structurally impossible rather than merely unlikely, and a
cancellation needs no counter to reconcile. A `remaining` column is a cache that
will eventually lie.

**Acceptance criteria.**

- **`durationMin` is the most important field in the form**, because it is the
  single most valuable attribute OSM does not carry. The form says so.
- Price is an integer-paise stepper, never a free-text amount.
- Accessibility is three-state per field: true, false, **or unknown**. A provider
  who does not know must be able to say so. Otherwise we either misrepresent them
  or silently drop them from every accessible search.
- Availability is entered as recurring weekly slots with a capacity each, plus
  one-off overrides. The provider sees the derived availability and the calendar
  that produced it.
- Provider-submitted fields are `provenance: 'provider'`, distinguishable from our
  curation at a glance.

**Failure behaviour.**

- Unknown accessibility → `null`, treated as unknown by the gate, shown as unknown
  in the UI. Never coerced to `false`.
- Provider edits a duration that invalidates a plan already shown to a traveller:
  the change is timestamped, and the next plan recomputes. We do not retroactively
  rewrite a plan someone is standing in the middle of.
- No availability set → the listing appears for discovery but is marked
  walk-in-only or unavailable, per the provider's `booking` fields.

## 10. Feature: unmet demand and provider opportunity

**Purpose.** Close the loop. A search that returned nothing usable is the most
valuable dataset in the product: it is a list of what travellers want and cannot
get.

**User story.** *As a provider, I want to know what people nearby searched for,
could not get, and which single constraint eliminated them — so I know what to
change.*

**Input.** Every zero-result search: the context minus anything identifying, the
`shortfallCount`, and which `RejectionCode` killed the most candidates.

**Output.** Two distinct values, in this order:

| Type | What it is | Audience |
|---|---|---|
| **`UnmetDemand`** | one logged search: constraints, shortfall count, `topBlockingCode`, `topBlockingCount` | internal, aggregated |
| **`ProviderOpportunity`** | one actionable suggestion: `kind`, a finished `headline`, `evidence[]` of label/value pairs, a `cta` | provider-facing |

`ProviderOpportunity.kind` is one of `unmet_search`, `capacity_window`,
`listing_quality`, `must_see_gap`.

**Acceptance criteria.**

- **Every suggestion carries a count.** A suggestion without evidence is
  marketing copy, and we would be lying. The `evidence` array is not optional in
  spirit even though the schema allows an empty one.
- The `headline` is a finished, actionable sentence naming the change:
  *"Add a Thursday 17:00 slot — 42 travellers near you wanted a step-free craft
  workshop under ₹500 and you were the only match within 2 km."*
- The action is one click: open the listing at the exact field in question, or
  open the availability grid with the suggested window pre-selected.
- **Never suggest something already offered.** Cheap check, permanent credibility.
- `UnmetDemand` stores constraints, never identity. No PII in the analytics path.
- Suggestions are measured after the fact. If a suggestion type is never acted on
  and never moves match rate, it is cut — a dashboard of suggestions nobody acts
  on is worse than none.

**Failure behaviour.**

- Too few searches to be confident → no suggestion. We do not extrapolate from
  three data points into a recommendation.
- A suggestion whose evidence would identify an individual → suppressed.
- The nearest matching provider does not exist → the gap is recorded as a
  `must_see_gap` for acquisition, not pushed at a provider who cannot serve it.

## 11. Feature: booking

**Purpose.** Let a traveller act on a recommendation, and let a provider commit
without either side being exposed to a double-booking.

**User story.** *As a traveller, I want to request a slot and know its state. As a
provider, I want to accept or decline, and be asked why when I decline.*

**Input.** A `Slot` and a `BookingRequest` with party size and contact.

**Output.** A `BookingRequest` moving through `BOOKING_TRANSITIONS`, plus a
`booking_events` audit row per transition.

```
requested ──► confirmed ──► completed
    │             │
    ├──► declined └──► cancelled
    └──► cancelled
```

**Scope: listings and requests only. No payments, no commission, no payouts, no
refunds, no disputes.** That is a deliberate cap, not an omission.

**Acceptance criteria.**

- Illegal transitions **throw at runtime**, and are not offered in the UI.
  `state` and `status` are orthogonal axes, not one field.
- **Oversell is prevented in this order**, because the order is the whole point:

  ```
  1. begin transaction
  2. take the lock        (advisory, transaction-scoped, 3 s timeout)
  3. RE-COUNT from source of truth   (never trust a cached remaining)
  4. ASSERT sufficient
  5. insert the booking row
  6. commit — lock releases
  ```

- **Idempotency by deterministic transaction id**, so a double-clicked confirm
  cannot decrement capacity twice.
- Cancelling has a different effect from confirming: `compensateInput ≠ output`.
- **Declining requires a reason.** The traveller is told, and the reason feeds
  provider `reliability`. Asking is the reputation play.
- Every transition records actor, timestamp and note.

**Failure behaviour.**

| Situation | Behaviour |
|---|---|
| Slot filled between display and request | Re-count finds zero; return "just taken", suggest the next slot. Never oversell. |
| Lock timeout | Retry, then "busy". Not a 500. |
| Provider never responds | Traveller sees the state is still `requested`, with no implied confirmation. |
| Requested slot is later cancelled by the provider | Traveller is notified, and `travellerNotifiedAt` is set. |

## 12. Feature: analytics

**Purpose.** Give the provider the two numbers that actually change behaviour,
and give us the eval signal.

**User story.** *As a provider, I want to know impressions, requests, acceptance
rate, and why people declined — not a vanity score.*

**Input.** `Interaction` rows, `BookingRequest` history, `ReplanResult` swaps.

**Output.** Impressions · fit-views · requests · acceptance rate · **decline
reasons** · listing quality with the *measured* effect of each fix.

**Acceptance criteria.**

- Decline reasons are surfaced as a distribution, because "12 people declined
  because of capacity" is a business insight and an average hides it.
- A listing-quality claim carries a measured number, or it is not printed. *"Adding
  a photo"* is useless without *"→ N× more fit-views, measured across M listings."*
- Traveller-facing: time utilisation, swaps per replan, and the constraint that
  eliminated the most candidates.
- The eval table is regenerated on every run and committed, so a regression is
  visible in the diff.

**Failure behaviour.**

- A metric we cannot measure is not displayed. An empty panel is honest; a
  confident wrong number is not.
- Small samples are shown as small samples, with the count attached.

## 13. Feature: LLM fallback and offline behaviour

**Purpose.** The demo must not die on a rate limit, and the product must not lie
about what it knows.

**User story.** *As a traveller on a bad connection, I want the product to keep
working and to tell me when it is working with less information.*

**Input.** Any external dependency: Overpass, OSRM, Valhalla, Nominatim,
Open-Meteo, images, the LLM provider.

**Output.** A working `Plan` in every case, plus an honest label on whatever
degraded.

**Acceptance criteria.**

| Call | Cache | Fallback |
|---|---|---|
| Overpass | SQLite, keyed by rounded bbox | committed offline snapshot |
| OSRM / Valhalla | SQLite, keyed by coord pair + profile + time band | haversine × mode speed factor, `estimated: true` |
| Nominatim | SQLite | city centroid from `CityManifest` |
| Open-Meteo | 30 min TTL | simulated condition, labelled `source: 'simulated'` |
| Images | on disk, with attribution | category placeholder |
| LLM | keyed by the **deterministic result**, not the prompt hash | regex parser |

- **`LLM=off` produces a full plan.** Not a degraded one. This is the credibility
  anchor, and the eval suite must pass in that mode.
- Caching LLM output keyed by the deterministic result is deliberate: caching raw
  text in front of structured output is a hallucination amplifier. We cache the
  **narration**, never the **decision**.
- Every degradation is visible. A simulated forecast says `simulated`. A modelled
  leg says `estimated: true`.

**Failure behaviour.**

- All network calls fail → committed snapshot, full demo path.
- LLM returns unparsable output → `LLMEnvelope.degraded: true`, deterministic
  parser, log the reason and the model that answered.
- `LLM_ENVELOPE` is `.strict()`, so an unexpected key is a parse failure rather
  than a silently ignored field.

## 14. Feature: accessibility

**Purpose.** Make access needs satisfiable exactly, not approximately. This is a
graded factor and it is the one OSM populates least.

**User story.** *As a traveller using a wheelchair, I want step-free access to be
a guarantee, and I want to know which parts of the answer are verified and which
are inferred.*

**Input.** `accessNeeds: AccessNeed[]` on the `DiscoveryContext`; the six
tri-state `Accessibility` booleans on each `Experience`.

**Output.** A plan where every stop passes every declared need, plus per-need
verification state on screen.

**Acceptance criteria.**

- Needs are **booleans, never a score.** "I need step-free" is either satisfied
  exactly or not at all.
- A three-state field is modelled honestly. `null` means unknown and is not
  collapsed to `false` — collapsing it is how a wheelchair user gets shown twelve
  venues with twelve steps.
- Derived availability is exposed per need: which stops are verified step-free,
  which are provider-asserted, which are inferred.
- Keyboard navigable through every flow. Non-negotiable, and it is close to free.
- `prefers-reduced-motion` honoured everywhere. Non-negotiable.
- Focus is visible, contrast meets AA, and the plan is fully usable as a list —
  the map is an aid, not the only view.
- Every need has a `RejectionCode` so a failure is explainable:
  `not_step_free`, `not_stroller_ok`, `no_low_stairs`, `no_hearing_loop`,
  `no_restroom`, `inaccessible`.

**Failure behaviour.**

- Every nearby option fails a need → say so, name the need that eliminated the
  most candidates, and show the verified options within a wider radius with their
  extra travel time priced in. Never silently drop the need.
- A need cannot be verified for a listing → it is shown as unknown, with the
  provider's contact route, not as satisfied.

## 15. Data and provenance

**Purpose.** Say where every fact came from, and never blend a curated fact with a
guess.

**User story.** *As a traveller, I want to know whether "step-free" was verified
by someone, claimed by the owner, taken from OpenStreetMap, or guessed by a model.*

**Input.** `Sourced` and the per-field `Experience.provenance` record.

**Output.** A visible badge and a confidence number on anything `inferred`.

**Acceptance criteria.**

- Five provenances, no ambiguity: `curated` (a human wrote it) · `provider` (the
  listing's owner submitted it) · `osm` (harvested) · `inferred` (a model guessed
  from name and category — lowest trust, always shown) · `derived` (computed by
  our engine).
- Curated facts carry `confidence: 1`. Only `inferred` fields carry a real
  confidence.
- Where OSM falls short is a measured, committed number, not an assertion. From
  `data/reference/osm-tagging-schema/`, across **1,739 iD presets**: `opening_hours`
  appears in **8.9%**, `wheelchair` in **6.2%**, `fee` in **4.1%**, and
  `diet:vegetarian` and `wheelchair:description` in **0%**. **1,468 of 1,739
  (84.4%) carry no gate field at all.** That is why the curated layer exists, and
  why absent is `unknown` rather than `fail`.
- OSM has no ratings. Ratings come from provider-submitted reviews, Bayesian-
  smoothed, with the sample size shown.
- **We do not scrape Google Maps, Instagram, Zomato or Tripadvisor.** It would
  fill the ratings gap and it breaches their terms. The equivalent is
  provider-submitted data, which is what a real marketplace has anyway.
- Every external fact records the endpoint that served it.

**Failure behaviour.**

- Field absent → `null` plus a badge, never a default that reads as a fact.
- External endpoint down → the committed snapshot, and the `source` field names it.
- Attribution missing for an image → the image is not shown.

## 16. City portability

**Purpose.** Make adding a city a data task, so the engine never hardcodes a
place.

**User story.** *As the team, I want to add Navi Mumbai without touching engine
code, and prove the routing model handles a planned grid and ferry corridors.*

**Input.** A `CityManifest`: slug, display name, bbox, centre, timezone, currency,
neighbourhoods, `monsoonMonths`, `congestionModel`, `transitCorridors`.

**Output.** A city that behaves correctly, including a second one across water.

**Acceptance criteria.**

- No city-specific logic in `src/engine/`. Geography arrives through the manifest.
- Navi Mumbai is in scope because it stresses the model properly: planned grid
  versus island city, ferry corridors, a genuinely different travel-time
  structure. Ferry and rail corridors are what prove the routing model is real.
- `congestionModel` is a **documented heuristic and labelled as one**, not truth.
- `transitCorridors` carry in-vehicle time plus wait, and transfers, because
  "21 minutes" without the wait is a lie.

**Failure behaviour.**

- A corridor is not seeded → fall back to a haversine estimate and mark the leg
  `estimated: true` with a `detail` that says the mode is a guess.
- A city manifest is missing a field → the manifest fails validation at the
  boundary, and the city does not half-load.

## Architecture in one page

```
        user text
            │
            ▼
    ┌───────────────────┐
    │  LLM              │   natural-language understanding only
    │  → DialogueDecision  { contextPatch, reply, confidence, suggestions }
    └─────────┬─────────┘
              │  contextPatch — the only permitted effect
              ▼
    ┌───────────────────┐
    │  DiscoveryContext │   the situation, plus `original` kept forever
    └─────────┬─────────┘
              ▼
    ┌───────────────────────────────────────────────┐
    │  DETERMINISTIC ENGINE — pure TypeScript       │
    │                                               │
    │  ① retrieve   text + tags + isochrone         │  ~120 candidates
    │  ② feasibility  12 hard gates, every drop     │  ~12–25   → Rejection[]
    │                emits a Rejection             │
    │  ③ scoring    one scalar, named components   │
    │  ④ packing    cluster → route                │  2–4 stops
    │  ⑤ validation independent recompute           │  reject on drift
    │  ⑥ relax      named ladder, says what it gave up
    └─────────┬─────────────────────────────────────┘
              ▼
            Plan
     stops + legs + Fit + ScoreBreakdown
     + Rejection[] + relaxations + stress
              │
              ├─► traveller:  why this · why not that · the swap diff
              └─► provider:   aggregated Rejection[] → Unmet Demand
                                                          → Provider Opportunity
```

### Why the LLM is not allowed to build the itinerary

Because a language model cannot be held to a constraint, and this product's entire
value is that it holds them.

| If the model chose the stops | Consequence |
|---|---|
| A stop is closed at the visit time | Nothing catches it. There is no arithmetic to be wrong about. |
| The chain overruns the window | Discovered by the traveller, on foot, in the rain. |
| The plan costs ₹2,400 on a ₹1,500 budget | The same. |
| A step is not actually step-free | Someone in a wheelchair finds out at the door. |

A model can produce a fluent itinerary that violates all four. Nothing in the
output tells you it did, because the output is prose and prose does not fail
loudly.

A solver either satisfies the constraint or it does not, and we can check which
in microseconds. So we split the job:

| Job | Who | Why |
|---|---|---|
| Understand "my aunt can't do stairs" | LLM | Language is the model's whole advantage. A regex gets this wrong. |
| Decide what fits | Engine | Arithmetic. Verifiable, reproducible, fast. |
| Say why in a sentence | LLM | Presentation, after the fact. Cannot change the answer. |
| Check the answer | Validator | Independent recompute. Catches a buggy packer, and it catches us. |

The boundary is enforced, not promised:

1. `DialogueDecision` is `.strict()` with eight permitted patch keys. It cannot
   express a recommendation, an ordering, or a feasibility result.
2. A test makes an LLM import inside `src/engine/` a **build failure**.
3. `ValidationResult` recomputes the objective from the emitted `Plan` and rejects
   on `objectiveDelta > 1e-6`. A negative test corrupts a plan and asserts the
   validator catches it.
4. The whole eval suite passes with `LLM=off`.

We looked at this rather than assuming it. Across the reference set, the failure
mode is consistent: the projects that leaked let the model write the **ordering**,
then tried to catch it with a prompt. The ones that survived paired the model with
a **validator**. The strongest single artifact we found is FloatTrip's
`validate_solution`, which re-derives the objective and hard-fails after one
repair round. We took the pattern. We are not claiming it is unique — three of the
projects we read keep the LLM out of the decision path, and several carry
structural boundary tests.

An unsat-core relaxation would be a nicer story than our named ladder. The
reference implementation we would have copied calls `unsat_core()` on a solver
with zero tracked assumptions, so it always returns empty, and the `minimize` /
`maximize` pair on one optimise object is lexicographic, so the penalty is
lowest-priority and the relaxation is silently defeated. A named ladder that says
what it gave up is both simpler and true.

## Acceptance: what a judge should be able to do unaided

1. Drop a pin, say *"three hours, ₹1,500, four of us with parents, it may rain"* →
   get a chained `Plan` where every stop carries a `Fit` and a visible reason.
2. Say *"it started raining"* → the plan re-solves, shows the swap diff, and keeps
   the original intent on screen.
3. Say *"my parents are tired"* → walking drops, dwell time rises, and the diff
   says so.
4. Say *"make it cheaper"* → the plan re-solves against the new ceiling and names
   what it cut.
5. Tap something that is missing → get a specific reason with a number, and three
   actions.
6. Switch to the provider view → traveller demand becomes **Unmet Demand** becomes
   a **Provider Opportunity**, with the count that justifies it.
7. Turn on `LLM=off` → all of the above still works.

Points 1–6 are the demo. Point 7 is what makes it credible.

## Roadmap

Each phase states what becomes true, and what has to be true first. Dates are
deliberately absent: this is a one-week build and a fake date is worse than none.

### Phase 1 — Context-aware discovery · **built now**

Capture the situation, gate on twelve hard constraints, rank what survives, pack it
into a chained `Plan`, validate it independently.

*Exit condition:* a `Plan` for any context in the eval suite, `LLM=off`, zero
constraint violations.

### Phase 2 — Live replanning · **built now**

`ContextChange` triggers, diff against `original`, minimal swap sets, named
relaxation ladder.

*Exit condition:* ≤ 2 swaps per trigger across the adaptation scenarios, with
`preservedIntent: true`.

### Phase 3 — Traveller memory

Move from a session-scoped context to a durable one. What the traveller has done,
what they rejected and why, which constraints were non-negotiable last time.
Still visible, still editable, still deletable — the bandit already emits a
`WeightProfile`; this persists it and lets a constraint be *sticky* rather than
re-typed.

*Needs:* a real auth identity to hang the profile on, and a privacy story for
retention.
*Blocked by today because:* a `WeightProfile` with `observations: 0` is not
memory, and pretending otherwise is how a recommender becomes creepy.

### Phase 4 — Experience graph

Move retrieval from FTS5 + tag facets to the three perception dimensions —
landscape, activities, atmosphere — as separate vectors, behind the existing
`Embedder` interface. The schema is already in the contract; the vectors are not.

*Needs:* an embedder, a vector store, and the three per-experience rows the schema
already anticipates.
*Watch out:* the reference implementation we would copy normalises its weights
incorrectly and computes all three cosines in one pass with a `0.6/0.5/0.5` blend.
Keep the dimensions separate, or we reproduce its bug.

### Phase 5 — Provider intelligence

Turn the Provider Opportunity feed from *reactive* to *predictive*. Not just
"N travellers wanted this and could not get it" but: which provider should be
approached about which gap, in which neighbourhood, with what expected effect — and
then whether it actually moved match rate.

*Needs:* enough logged `UnmetDemand` to be worth modelling, and Phase 3's memory to
know repeat demand. Until then the reactive feed is the honest version.
*The trap:* a dashboard of suggestions nobody acts on is worse than no dashboard.

### Phase 6 — Multi-city platform

Second city done properly rather than five done badly. `CityManifest` is already
the seam: geography, monsoon months, congestion model, transit corridors are all
data. Navi Mumbai first, because ferry and rail corridors are what prove the
routing model is real.

*Needs:* the routing facade to be the only thing that knows about distance, and a
harvest path that does not depend on one blocked Overpass host.
*Honest limit today:* the city-agnostic claim is a design property with one city
loaded. A second city is the proof, and it has not happened yet.

### Not on this roadmap, on purpose

Payments, commission, payouts, disputes · multi-day itineraries · real-time crowd
or "vibe" sensing · multi-agent group negotiation · learning-to-rank · native
mobile apps · offline sync.

## Terminology

These names are fixed. If a document or a screen needs a new concept, it does not
get a new name.

| Name | Means | Type |
|---|---|---|
| **Ananta** | The product. Nothing else. | — |
| **DiscoveryContext** | The traveller's situation: window, budget, party, needs, weather, and `original` | `src/contracts` |
| **DialogueDecision** | The only LLM output that may affect anything. A `contextPatch`, a `reply`, a `confidence`, `suggestions` | `src/contracts` |
| **Experience** | One catalogue row: all attributes, per-field provenance | `src/contracts` |
| **Plan** | The packed, chained, time-boxed itinerary, with `rejected[]` | `src/contracts` |
| **Replan** | Re-solving the `Plan` against a changed `DiscoveryContext`, diffed against `original` | `src/contracts` (`ReplanResult`) |
| **Unmet Demand** | One logged search that returned nothing usable, with the constraint that killed the most candidates | `src/contracts` (`UnmetDemand`) |
| **Provider Opportunity** | One actionable suggestion to a provider, built from aggregated Unmet Demand | `src/contracts` (`ProviderOpportunity`) |

Supporting names that are fine because they are **UI surfaces rendering a
contract type**, not competing product names: the feasibility meter (`Fit`), why
this / why not that (`ScoreBreakdown` / `Rejection`), the relaxation ladder
(`RelaxationApplied.rung`), the stress score (`Plan.stressScore`), provenance
badges (`Provenance`).

Two retired names, for the record: **ATHITI** was the research codename and
**TripFit** a working name. Neither appears in product copy.
