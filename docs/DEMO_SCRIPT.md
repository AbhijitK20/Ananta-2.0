# DEMO SCRIPT — Ananta

> **2 minutes 20 seconds of stage time, three minutes maximum.** Rehearse until
> beats 3 and 4 are boring. The fallback branches exist because wifi is a lottery.
>
> **Nothing in this script contains a result.** Every number you say on stage is
> one you read off the screen in front of you. If `docs/EVAL_RESULTS.md` has not
> been generated by `npm run eval`, you do not have an eval table, and you say
> "we haven't run it yet" rather than inventing a row.

---

## The spine

| Beat | Time | What it proves | Fails if |
|---|---|---|---|
| 0 | 0:00 | the problem is real and named | — |
| 1 | 0:20 | a situation, not a query | you read a form aloud |
| 2 | 0:40 | fit is enforced, and the work is shown | no fit meter, or a list instead of a chain |
| 3 | 1:00 | it re-solves when reality changes | more than 2 swaps, or intent lost |
| 4 | 1:20 | it adapts to the people, not just the clock | walking does not drop |
| 5 | 1:40 | budget is a constraint, not a filter chip | cost does not change |
| 6 | 2:00 | the loop closes for the provider | no count behind the suggestion |
| 7 | 2:20 | what it actually is | — |

Beats **2 and 6** are the ones that are ours. Everyone can show a list of places.
Showing that a rejection is a *number and an action*, and that the same record
becomes a provider's demand signal, is a product decision.

## Pre-flight — 15 minutes before

- [ ] `npm run db:seed` run; catalogue loaded
- [ ] `npm run dev` up; the pinned scenario is already in the URL as a
      `DiscoveryContext` deep link, so you are not typing under pressure
- [ ] **Wifi off, then run the whole path once.** The demo must not touch the
      network
- [ ] `LLM=off` toggled once, so you know the fallback is live before you need it
- [ ] Two accounts signed in: traveller and provider, in two tabs
- [ ] Browser at 1440×900, zoom 100%
- [ ] Images cached locally with attribution, or placeholders rendering
- [ ] `npm run eval` run **and only if it is green** — see beat 7
- [ ] Tab 2 open on the same route, as a backup

**Know before you present, because a judge will find it in the data:** the
catalogue and the review set are synthetic. Every record in `content/**` carries
`synthetic: true` and a `__meta.estimateBasis`, and inferred fields carry
`provenance: 'inferred'`. There are no users, so the Unmet Demand log is seeded.
The mechanism, the gate, the packing, the validation and the replanning are real.
Say which is which before you are asked.

## Beat 0 · 0:00 — The problem

**Say:**

> "Travel apps know where places are. They don't know what is actually possible
> for this traveller, right now."

Then, while the screen is still on the title:

> "Three hours. Fifteen hundred rupees. Four people, and one of them is my
> father, who can't manage stairs. It might rain.
>
> Every app on your phone will happily list forty restaurants. It will not tell you
> that eleven of them are shut right now, that the good ones are forty minutes away
> in traffic, that none of them are step-free, and that the one your kid would love
> costs more than the whole budget.
>
> And the same failure runs the other way. The potter two kilometres from this
> hotel has no way to reach the person standing in front of it."

**Do not** apologise for the setup. Do not explain the tech yet.

## Beat 1 · 0:20 — The traveller

**Do:** drop a pin on a Colaba hotel. Set the window to **3 hours**, party **4**,
budget **₹1,500**, toggle **step-free**, add child age. Then type the sentence in
the chat sidecar:

> "I have three hours in Mumbai, fifteen hundred rupees, I'm with my parents and it
> may rain."

**Type it exactly as written.** Every sentence on this page is a phrase the
deterministic parser in `src/llm/nlu.ts` matches, so the whole demo plays
identically with the model switched off, on a flat network, and on a bad wifi
minute. The words are counted, not guessed:

| Type this | It becomes |
|---|---|
| "I have three hours in Mumbai, fifteen hundred rupees, I'm with my parents and it may rain." | `availableMin: 180`, `budgetMinor: 150000`, `accessNeeds: ['lowStairs']`, `indoorOnly: true` |
| "something local, not a chain" | `interests: ['local']` |
| "it started raining" | `indoorOnly: true` |
| "my parents are tired" | `accessNeeds: ['lowStairs']` |
| "my aunt can't do stairs" | `accessNeeds: ['wheelchair']` |
| "I have only 90 minutes." | `availableMin: 90` |
| "Less walking." | `avoid: ['long walks']` |
| "Indoor only." | `indoorOnly: true` |
| "make it cheaper" | budget × 0.7, rounded to a rupee |
| "nothing too crowded" | `avoid: ['crowds']` |
| "actually make it ₹600" | `budgetMinor: 60000` |
| "something for a 6 year old" | `interests: ['family','kid_friendly']` |
| "Is it far?" | **no patch** — answered from the plan |

Spelled-out figures are parsed, so "three hours" and "fifteen hundred rupees" are
as safe as "3h" and "₹1500". Do not improvise a constraint you have not said
above: an unparsed phrase returns a low-confidence answer and asks you a question
instead of replanning, which is the correct behaviour and the wrong thing to
discover on stage.

**Say:**

> "That's not a search query. That's a situation. The difference is that a query
> gets you a ranked list, and a situation gets you a set of hard constraints that
> anything has to survive before it is allowed to appear."

**Point at** one thing only: the original context is still visible and unchanged.
Everything from here is a *re-solve of the same intent*.

## Beat 2 · 0:40 — The contextual plan

**Say:**

> "This is not a list. It's a chain. Every stop has travel time to the next one,
> and the whole thing adds up to the window I said I had."

**Then walk six things, in this order. Eight seconds maximum each.**

| # | Point at | Say |
|---|---|---|
| 1 | **time** — the totals bar | "Total time used against the three hours I gave it. The utilisation number is on every plan, because 'respects your window' should be a measurement, not a claim." |
| 2 | **budget** — the cost line | "Fifteen hundred is a ceiling, applied as price times party size, and there's an optional stricter per-person limit on top." |
| 3 | **fit** — the feasibility meter on a card | "Every card shows activity, travel and buffer against what's left. That block in the alarm colour is what didn't fit. Most apps never show you the overflow at all." |
| 4 | **route** — the connector between two stops | "Twelve minutes' walk, 850 metres. Real routing, plus a congestion multiplier, and the leg is labelled as an estimate because it is one." |
| 5 | **why this** — the ledger on the card | "Why this one, as ranked contributions. These are numbers we computed. Not a sentence a model wrote to sound convincing." |
| 6 | **provenance badge** | "And this badge says where the fact came from — curated, from the owner, from OpenStreetMap, or inferred by a model. That last one matters, and I'll come back to it." |

**Then the differentiator, in one sentence:**

> "Now tap anything that *isn't* in the plan."

Tap a well-known expensive attraction that didn't make it. The panel gives the
specific constraint and the number.

> "It doesn't say 'no results'. It says which constraint killed it, by how much, and
> offers three things I can do about it. That panel is the product."

**Click "add 40 minutes."** The plan grows.

> "That's the whole idea. A rejection is not a dead end. It's a price, and you get to
> decide whether it's worth paying."

## Beat 3 · 1:00 — It started raining

**Do:** click the rain trigger, or type *"it started raining"* in the sidecar.

**Say:**

> "That is not a new search. It is a re-solve of the same intent against a world
> that changed."

**Point at, in this order:**

1. **The swap diff** — what left, what arrived, and the reason for each.
2. **"Still looking for: local food, something local"** — on screen, unchanged.
   Say it out loud, because this is the line that lands the architecture.
3. The stress score and its one rescue move.

**Say:**

> "We keep the original context forever and re-solve against that, never against
> the last change. So a chain of four reality-changes still converges on what you
> actually asked for. We never quietly replace someone's goal."

**If it breaks:** if a replan returns more than two swaps, say so out loud —

> "That's three swaps, which is over our own target of two. Here's the eval
> scenario that catches it."

Being honest about a known failure with a named test is more persuasive than a
smooth demo, and it is the one thing a smooth demo cannot buy you.

## Beat 4 · 1:20 — My parents are tired

**Do:** type *"my parents are tired"* — or hit the low-energy trigger.

**Say:**

> "Different thing. This isn't a clock problem, it's a people problem. Walk time
> drops, dwell time goes up, transfers get penalised, and it re-solves again."

**Point at** the walking total before and after, and the `mood` field in the
context patch. The model did not rewrite the plan. It emitted a **patch to a
constraint object** — eight permitted keys, nothing else — and the deterministic
engine rebuilt the plan from it.

**If asked what the model can touch:** that. It cannot name a recommendation,
reorder a plan, or edit a feasibility result. A test fails the build if that
changes.

## Beat 6 · 2:00 — The provider opportunity

**Do:** switch to the provider tab. Open the Unmet Demand view.

**Say:**

> "Now the other half. Every rejection I just showed you is a record. Aggregate
> those records and you get the most useful dataset in this product: a list of what
> people nearby wanted and could not get, and which single constraint eliminated
> them.
>
> That is traveller demand, becoming unmet demand, becoming a specific thing for a
> provider to do about."

**Then say this, unprompted, if the Unmet Demand rows are seeded** — and they are:

> "One thing I want to be straight about: we have no users yet, so the unmet-demand
> log in this demo is seeded, and every record in our catalogue is marked synthetic
> in the data — there is a `synthetic: true` flag on each one. The *mechanism* is
> real. The *counts* are not, and we would rather you knew which is which."

That sentence costs four seconds and it is the difference between a demo and a
claim. A judge who later finds a `synthetic` flag in the data will assume you
wanted it hidden; a judge who heard you volunteer it will ask better questions.

**Walk the chain on screen, pointing at each step:**

```
traveller demand   →   Unmet Demand   →   Provider Opportunity
(a zero-result        (logged with          (one action, with the
 search + the          blocking              count that justifies
 blocking reason)      constraint)           it)
```

**Point at:**

- the **count**. If there is no count, do not show the suggestion — a suggestion
  without evidence is marketing copy.
- the **cta**, which is one click: it opens the listing at the exact field, or the
  availability grid with the window pre-selected.

**Say:**

> "The provider doesn't need a marketing budget and doesn't need a marketplace.
> They need to know that fourteen people searched for a step-free craft workshop
> under five hundred rupees on a Thursday, and that step-free access is the reason
> all fourteen got nothing. That's one field on a listing, and it's the highest-value
> suggestion we will ever make them."

Then close the loop out loud:

> "It's the same record. Nothing is logged twice."

**Say:**

> "Ananta doesn't just recommend places. It continuously finds what is actually
> possible — for this traveller, in this window, on this budget, with these people,
> right now. And every place it decides against, it tells you why, with a number
> you can act on."

**Then, if `npm run eval` has been run and is green**, open the results and read
the **actual** numbers off the screen:

> "Twenty-eight scenarios with human-labelled acceptable sets, run automatically,

> budget. The suite passes with the model switched **off** entirely.
>
> Here is the utilisation row. That is the whole argument for the architecture, in
> one number."

**Then toggle `LLM=off` and re-run one search live.** This is the credibility beat:

> "Everything you just watched was computed by a deterministic engine. The language
> model does one job: turn what you *said* into a constraint. Everything you *see*
> is arithmetic. Which is why the eval suite still passes with the model switched
> off entirely — and why I can show you this on a dead network."

**If `npm run eval` has not been run, do not fake a table.** Say instead:

> "The eval suite is written — 28 scenarios with human-labelled acceptable sets. We
> haven't run the final table yet. What I can tell you is that it passes with the
> model off, and here's the negative test that proves the validator works."

Then show the corruption test. Honest and specific beats a confident number that
collapses under one question.

## If you get asked mid-demo

**"Isn't that just a chatbot?"** No. The model emits a patch to a constraint object
and nothing else. It cannot name a recommendation or reorder a plan, and a test
fails the build if that changes.

**"Are the travel times real?"** Real routing plus a documented congestion model,
because free-flow times understate peak Mumbai. And we label the estimate as an
estimate. Where we fall back to a straight-line estimate, the leg says
`estimated: true`.

**"Is the weather live?"** When Open-Meteo answers, yes, and the source says `live`.
When it doesn't, the source says `simulated` and you can see that on screen. We
don't present a simulated forecast as a real one.

**"Where does the data come from?"** OpenStreetMap for the spatial backbone, hand-
curated for the fields it doesn't have, provider-submitted for the rest, and model
inference for the long tail — labelled as inferred, on screen, with a confidence.

**Anything you don't know?** "I don't know, and I'd rather say that than guess. It's
in our eval spec as a scenario we expect to fail." We publish three.

## Fallback branches

| If | Then |
|---|---|
| **No network** | Everything runs from the committed snapshot. Do not apologise. Say: "this is running entirely offline, which is the point." |
| **LLM times out** | The deterministic parser takes over inside the two-second budget. Narrate: "that fell back to the regex parser — same result, because the model was only parsing." |
| **Plan is thin** (under 2 stops) | Switch to a four-hour window. A good four-stop plan beats a thin two-stop one, and the mechanism is the same. |
| **Map is slow or blank** | Switch to list view. The list is a first-class surface, not a fallback — the whole demo works in it. |
| **Provider view is empty** | Open the Unmet Demand view directly and narrate the aggregation from the traveller-side rejections you already showed. |
| **The eval table is missing or red** | Do not present numbers. Present the negative test: corrupt a plan, show the validator catching it. |
| **Anything is broken** | "Let me show you the eval harness instead." Talk about the scenarios. **Never debug on stage.** |

## Likely judge questions

Fourteen, with the short answer. Have the long answer ready for the two or three
that matter.

### 1. "Why not just use ChatGPT for this?"

Because a language model cannot be held to a constraint, and this product's entire
value is that it holds them. Ask a model for a three-hour step-free plan for four
people under ₹1,500 in the rain and you will get a fluent, well-formatted
itinerary that is closed, over budget, over time, and not step-free — and nothing
in the output tells you which, because the output is prose and prose does not fail
loudly.

We use the model for the one job it is genuinely better at: turning *"my aunt can't
do stairs"* into a hard constraint. Then arithmetic decides.

### 2. "Why not Google Maps?"

Maps filters on what you typed. Everything that fails a constraint is still a
result — you find out it's closed when you get there. And it needs you to already
know what you want, which is the thing a time-constrained traveller does not know.

We return only what fits, and we tell you what didn't and why. The isochrone data
also shows a radius is the wrong shape: a 3 km disc is 3.2× the true 30-minute
walking area in Bandra West and excludes 73% of the true 30-minute driving area. One
radius cannot be right for both.

### 3. "Why not Tripadvisor?"

Reviews without structure. A five-star rating tells you nothing about whether the
place is step-free, how long it takes, whether it fits four people, or whether it
is open in the window you have. Reviews rank; they do not gate. And the top of a
Tripadvisor list for a city is a fixed set of the same famous places, which is the
opposite of local discovery.

### 4. "Why use an LLM at all?"

Because language is the model's whole advantage and we are deliberately not trying
to beat it there. A regex cannot reliably parse "we're exhausted" or "something
for a six year old" into structured fields. But it does not need to *decide*
anything. Three jobs: natural-language understanding, explaining a result in
sentences, and offline enrichment of missing catalogue fields. The third one only
ever writes fields tagged `inferred`.

### 5. "Why a deterministic engine instead of a solver?"

We planned to use Z3 and OR-Tools. Then we read the code. The npm Z3 binding is
officially maintained and unusable on Node — `init()` returns a module whose
high-level context is empty and whose low-level namespace exposes zero callable
functions. OR-Tools has no Node binding at all, and across 71 reference repositories
its routing library appears in none. And the paper we were going to copy gets its
own headline feature wrong: its unsat-core relaxation calls `unsat_core()` on a
solver with zero tracked assumptions, so it always returns empty, and mixing
`minimize` and `maximize` on one optimise object is lexicographic, so the penalty
is lowest-priority and the relaxation is silently defeated.

So we kept the technique — soft constraints as penalties with a minimised total —
and wrote it in about 150 lines of TypeScript inside our own search. One language,
no native dependency, and explainable in a sentence on stage.

### 6. "How do you control hallucination?"

Four mechanisms, all enforced rather than promised.

1. **The model cannot express a recommendation.** `DialogueDecision` is a strict
   schema with eight permitted context-patch keys. There is no field for a place
   name, an ordering, or a feasibility result.
2. **The boundary is a build failure.** A test fails the build if anything under
   `src/engine/` imports the LLM module.
3. **An independent validator recomputes the answer.** It re-derives the objective
   from the emitted plan and rejects on any drift over 1e-6. A negative test
   corrupts a plan and asserts the validator catches it.
4. **Inferred facts are labelled, per field.** `curated`, `provider`, `osm`,
   `inferred`, `derived` — and anything inferred shows a badge and a confidence.
   We never blend a curated fact with a guess without saying so.

The one gap we will name ourselves: a `null` accessibility field is unknown, and
unknown is not the same as false. We show it as unknown and give the traveller the
provider's contact route. We don't round it up to "yes".

### 7. "How does replanning work?"

The `DiscoveryContext` keeps an `original` copy that is never mutated, and the
replan diffs against that — never against the last change. So four chained
reality-changes still converge on the original intent.

Concretely: a change produces a small patch, the engine re-runs the same six stages,
and we compute a minimal swap set by pinning the stops that are still valid and
re-solving only the rest. Every swap carries a written reason and a score delta. If
nothing fits, we walk a named ladder — strict, dropped minimum, greedy fill, single
best — and the UI always says which rung we used and what it gave up. "Relaxed:
minimum one stop instead of two" is honest and demo-able. An unsat core would be
prettier, if the reference implementation actually had one.

Our target is two swaps or fewer per change. The eval suite measures it.

### 8. "How do you know it works?"

A fixed scenario suite with human-labelled acceptable sets — written from the
traveller's voice, not the schema's — run automatically, with the naive baseline
printed next to our numbers. The baseline is FTS5 text match, sort by rating, take
the top N, ignore time and budget: roughly what a competent engineer's first
afternoon produces, and what most submissions do.

Two rules keep it honest. Every scenario must pass with `LLM=off`; if a scenario
needs a model, it is testing the wrong thing. And the baseline is not a strawman.

We also published three scenarios we expect to fail, with the diagnosis. An eval
suite that cannot fail is not worth anything. The results file is regenerated on
every run and committed, so a regression shows up in the diff.

### 9. "How do providers actually benefit?"

They get told what people nearby wanted and could not get, and which single
constraint eliminated them. That is the acquisition channel, and it costs almost
nothing to build because the records already exist for the traveller-side
explanation.

The rules we hold it to: every suggestion carries a count, or it isn't shown; the
action is one click to the exact field; and we never suggest something already
offered. And we measure whether the suggestion moved match rate — if a suggestion
type is never acted on and never moves anything, we cut it. A dashboard of
suggestions nobody acts on is worse than none.

### 10. "How does it scale?"

City-agnostic by construction: geography arrives as a `CityManifest` — bbox,
monsoon months, congestion model, transit corridors — and no city-specific logic
lives in the engine. Adding a city is add a manifest, run the harvest, curate.

Being straight about the ceilings: FTS5 is fine to roughly 10k experiences, then
the quadratic clustering hurts and clusters get precomputed per grid cell. Around
50k, `node:sqlite` write serialisation becomes the wall and you move to libSQL or
Postgres with the same schema. Seeded transit corridors don't generalise, which is
why routing sits behind one facade that Valhalla and GTFS can slot into. None of
those decisions needs redoing to grow.

### 11. "How does it work without AI?"

Because the model is not in the decision path. It is three optional jobs: parsing
what you said, writing a sentence explaining a result, and offline enrichment of
missing catalogue fields. With `LLM=off`, the regex parser still builds the same
`DiscoveryContext`, the engine produces the same plan, and template narration
replaces the generated sentences. The eval suite passes in that mode — that is the
credibility anchor for the whole architecture.

### 12. "How is the data sourced, and how much do you trust it?"

Four layers, and we show the provenance of every one on screen.

OpenStreetMap is the spatial backbone. We measured how far it actually goes, from
committed data in `data/reference/`: across 1,739 iD presets, `opening_hours`
appears in 8.9%, `wheelchair` in 6.2%, `fee` in 4.1%, `diet:vegetarian` and
`wheelchair:description` in 0%, and 84.4% of presets carry no gate field at all.
OSM also has no ratings.

So the fields the product actually grades on — duration, price, capacity,
kid-friendly, step-free — are hand-curated or provider-submitted. Ratings come from
reviews, Bayesian-smoothed toward a regional prior with the sample size shown. The
long tail is model-inferred and labelled `inferred` with a confidence.

We do not scrape Google Maps, Instagram, Zomato or Tripadvisor. It would fill the
ratings gap and it breaches their terms. The equivalent is provider-submitted data,
which is what a real marketplace has anyway.

### 13. "How is accessibility handled?"

As booleans, never as a score. "I need step-free" is either satisfied exactly or
not at all — a weighted accessibility score would let a highly-rated restaurant
outrank a step-free one, which is precisely the failure.

The fields are tri-state, true / false / **unknown**, and that third state is the
whole design. OpenStreetMap's `wheelchair` field is three-state, so `null` is a
real answer, and collapsing it to `false` is how a wheelchair user gets shown
twelve venues with twelve steps. Unknown shows as unknown.

There is a `RejectionCode` for every need, so a failure is explainable rather than
silent. And the platform obligations hold: keyboard navigable through every flow,
visible focus, AA contrast, `prefers-reduced-motion` honoured, and the plan fully
usable as a list because the map is an aid and not the only view.

### 14. "How does personalisation work, and isn't that creepy?"

A Thompson-sampling bandit over the interaction stream produces a `WeightProfile`
— per-traveller weights over interpretable features like interest match, value for
money, and travel friction. Three things make it defensible.

It is **visible**: the traveller sees the learned weights, with the observation
count, and can edit or delete them. **Stated and learned never mix silently** — the
profile's `source` is `prior`, `learned` or `user_edited`. And it is
**interpretable**: every weight maps to a feature with a name a person can agree or
disagree with, which is the opposite of an embedding.

We deliberately rejected learning-to-rank. It needs training data we do not have,
and it produces numbers nobody can read. On a cold start the profile is the prior
with `observations: 0`, and the UI says so rather than implying we have learned
something about you.
